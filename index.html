Overview

From a single search bot to a multi-tenant platform

Access to digital books in Uzbek is fragmented and hard to search. A user types — or says — a title, and the bot returns matching results and delivers the file instantly. What began as one bot grew into a two-tier platform.

🤖

The Main Bot

A feature-rich library assistant: fuzzy & voice search, audiobooks, group delivery, reactions, favourites, comments, and a full owner/admin control surface.

🏷️

The White-Label Platform

Anyone connects their own @BotFather bot and instantly runs a branded book bot on the shared catalogue — with their own users, settings, usage limits, plan, and revenue.

Capabilities

Key Features

Discovery, delivery, acquisition, and engagement — built for real users in three languages.

🔍

Typo-tolerant search

Elasticsearch with fuzziness: AUTO and precision-controlled matching that returns the book you asked for — not noise.

🔤

Bilingual transliteration

Automatically searches Latin and Cyrillic variants — essential for Uzbek, where both scripts are in everyday use.

🎙️

Voice search

Send a voice note; speech is transcribed locally with faster-whisper and corrected against the catalogue.

⚡

Instant CDN delivery

Files served via Telegram file_id — cached on Telegram's CDN, so delivery is near-instant at zero server bandwidth.

📦

Large-file support

A self-hosted Telegram Bot API server (local mode) supports files up to 2 GB and removes cloud rate limits.

🛰️

Automated harvester

A Telethon worker watches source groups and backfills history with a resumable per-group cursor — a restart continues where it left off.

🧪

Quarantine review

Harvested books stay out of search until the owner approves them — airtight, so pending content never leaks into results.

📊

Demand analytics

Every zero-result search across all bots is aggregated into a ranked, data-driven roadmap of what to acquire next.

🚫

Reject-blocklist

Deliberately deleted titles are remembered so they can't silently re-add — with a one-tap un-reject escape hatch.

Single source of truthPostgreSQL is authoritative; Elasticsearch and Redis are optional accelerators — the bot degrades gracefully if either is down.
Dependency injectionbot.py is a composition root, wiring helpers into feature modules via a configure(deps) bridge — keeping modules decoupled.
Idempotency & retriesPayments, deliveries, and file operations are safe to retry, with exponential backoff on transient Telegram errors.
Fail-open safetyGuards such as forced subscription never lock users out on error — misconfiguration can't break access.

Production Engineering

Reliability & Security

This project runs as real infrastructure, and the engineering reflects that.

🔧

Reliability

  • ▹Supervised services via systemd — bot, job worker, cleanup worker, local Bot API, connected-bot units — all Restart=always.
  • ▹Automated backups — nightly PostgreSQL dumps, off-site rclone replication, and an independent restore-verification job.
  • ▹Health & monitoring — HTTP readiness endpoint, deduplicated owner alerts, encryption-key self-check, and a dead-man's-switch.
  • ▹Self-healing — crash detection, exponential-backoff restarts, and give-up alerting for white-label runtimes.
🛡️

Security

  • ▹Encrypted credentials — every connected-bot token is Fernet-encrypted; the key is kept outside the database and backed up separately.
  • ▹Secret hygiene — secrets injected via systemd EnvironmentFile; tokens, hashes, and session strings redacted from logs; owner-only log permissions.
  • ▹Least privilege — owner-only commands and per-tenant ownership checks gate every administrative action.
  • ▹Idempotent payments — Telegram Stars charges de-duplicated by charge ID in an auditable ledger, with refund support.
